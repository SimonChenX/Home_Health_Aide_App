# ⚠ 待补：发射器 BLE 协议

APP 要通过 BLE **直连发射器**读取血糖数据（需求 2.4），但平台现有文档只覆盖
「设备 → API 的上行数据格式」（平台 `Docs/device-protocol-v3.md`），**没有 BLE 侧的定义**。
拿到下面这些信息后，只需改 `src/device/protocol.uts` 的常量与 `src/device/ble.uts` 的 `parseFrame()`，
页面与本地换算逻辑不需要动。

| # | 项 | 用途 | 当前占位 |
| --- | --- | --- | --- |
| 1 | 广播名称前缀 或 广播里的 Service UUID | 扫描时精确过滤，避免连错设备 | `DEV_NAME_PREFIX = 'E115'` |
| 2 | 主 Service UUID | 建立连接后枚举服务 | `0000fff0-...` |

| 5 | 是否需要认证/配对（是否用「连接码/识别码」派生密钥） | 平台侧有「连接码」概念，需确认 BLE 是否也校验 | 未实现 |

## 为什么这些必须先确认

- **seq 对齐**：平台按 `(probe_id, seq)` 唯一去重。若 APP 上报的 seq 语义与设备 ingress 不一致，
  会造重复行或覆盖（平台已有 `seq` 分段约定：设备自增 / 补录 ≥ 9e7）。
- **raw 口径**：平台 `readings.raw_x10` 是**设备原始值**（校准的输入），补录行存的却是已校准值。
  APP 上报必须走「原始值」通道，否则会污染算法状态（平台已修过同类历史缺陷）。
- **温度**：平台 `temp_x10` 参与校准；若帧里没有温度，需要明确填 0 还是沿用上一帧。

## 临时方案（协议到位前）

- `PROTOCOL_READY = false`：连接/订阅链路真实调用，帧解析返回 `null`（不做假数据，避免污染平台）；
- 首页可展示平台侧最新值（`/dashboard/latest`）与本地缓存，趋势/医疗/家庭等页面**完整可用**；
- 拿到协议后：改常量 + 实现 `parseFrame()` + `readFlashHistory()`，即可打通实时读数。
