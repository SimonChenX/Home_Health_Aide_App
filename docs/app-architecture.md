# APP 架构与「省电 · 少交互」设计

> 需求原文（老板，2026-10-02）：**「APP 要能够读取发射器的血糖数据，但是矫正算法放API端，你要做一个方案，
> 既能读取展示当下的矫正后的血糖数据，又可以达到省电，减少与API端的网络交互。」**

## 1. 约束

- 矫正算法是 **x86-64 原生库**（平台 `Api/native/libalg_native.so`，算法 E115M），手机装不了、也不该装：
  它是血糖值的唯一事实来源，端上重算必然与平台显示不一致。
- 发射器数据取回后要**实时展示**；如果每条都问平台，288 条/天 × 每条一次请求 = 明显费电、费流量。

## 2. 数据流

```
        (BLE 直连, 本地, 0 网络)
发射器 ─────────────────────► APP：原始值 raw_x10 ──插值──► 显示矫正值 (mmol/L)
                                  │                        ▲
                                  │ 攒批(≤500/批)          │ 校准曲线(几十点,<2KB)
                                  ▼                        │ 一天一拉 / 版本变化时拉
                              WiFi+充电/手动 ──批量上报──► API
                                                           │ 原生算法「全量回放」
                                                           ▼
                                             平台 cal_x10（与网页端完全一致）
```

## 3. 关键接口：`GET /api/calibration/curve?probe_id=N`

平台侧实现：`Api/internal/handler/app_cal.go`（含 10 分钟服务端缓存）。

- 取该探头 **`source='device'` 的全量真实历史**（与平台「重新校准」同一口径：算法是**带状态的时间序列回放**，
  中途截断会重新进入预热期 —— 实测偏差可达 3 mmol/L，故必须全量回放）。
- 回放结果取**末尾 500 条**做映射表：按 raw 取中位数去噪 → **等张回归（PAVA）强制单调**（生理上 raw↑⇒血糖↑必然成立）。
- 返回：

```json
{ "probe_id": 2, "sn": "P2260107670KDN86", "algorithm": "E115M", "sensitivity": 1.28,
  "temp_x10": 292, "unit": "mmol/L", "scale": 10, "range": [14, 105],
  "points": [[14, 43], [15, 45], "..."], "samples": 15842, "warmup_skipped": 4,
  "accuracy": { "checked": 500, "avg_diff": 3.15, "max_diff": 17 },
  "version": "20261002-2-25142-34-1280-292", "generated_at": "...", "ttl_sec": 600 }
```

- `points` 的 value 与平台 `readings.cal_x10` **同口径（mmol/L ×10）**，APP 插值后除以 10 显示。

## 4. 实测精度（真实探头、真实历史，平台 `Scripts/api_cal_curve_check.py` 11/0）

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 平均偏差 | **0.32 mmol/L** | 映射表 vs 平台回放值（500 条） |
| 最大偏差 | **1.7 mmol/L** | 同上 |
| 独立复核 | 平均 0.21 / 最大 0.6 mmol/L | 另取 30 条设备读数，用返回表自己插值再比 |
| 曲线单调性 | 0 个回退点 | PAVA 处理后 |

APP 端显示时按接口返回的 `accuracy.max_diff` 标注「本地估算 ±」，联网时用平台回放值自动对齐。

## 5. 省电与网络交互

| 动作 | 频率 | 说明 |
| --- | --- | --- |
| BLE 读实时值 | 设备节奏（约 5 分钟） | 本地换算，0 网络 |
| 拉校准曲线 | ≤ 1 次/天（TTL 24h + 版本判断） | 探头配置/历史变了才变 |
| 批量上报读数 | WiFi+充电 ≥20 条，或手动，或积压 ≥500 条兜底 | 一次 ≤500 条 |
| 首页数据 | 启动/下拉刷新 | 不做定时轮询 |

对比「每条读数都问平台」：网络请求量下降 **≈99%**；屏幕常亮场景下蓝牙连接是唯一常驻开销。

## 6. 代码落点

| 文件 | 职责 |
| --- | --- |
| `src/core/cal-curve.uts` | 拉曲线、缓存、**本地插值**（`toCalibrated`）、不确定度 |
| `src/core/store.uts` | 登录态、当前探头、曲线缓存、待上报队列 |
| `src/core/sync.uts` | 同步时机与批量策略 |
| `src/device/ble.uts` | BLE 连接/订阅/读历史（协议见下） |
| `src/pages/*` | 首页、趋势、医疗、家庭、我的（UI 与平台同令牌） |
